## 发布前必须核对

- 用户明确要求部署后，再连接服务器检查 current 链接、发布锁、Nginx 与现有主站后端引用；不要把旧部署文档中的 current 当成实时值。
- 根目录并非单一 Git 仓库。源码审阅工作副本为 .ops/backup-20261018/PersonalWebsite 与 CashflowCalendar；本轮应保存到独立优化分支，记录实际提交和各应用构建摘要。之前发布版本保存在 production/，不因本轮本地构建而更新。
- 备份前轮已验证，但原 WebsiteBackup-20261018 路径本轮未找到；用户可能另行保管，不能假称再次验证。发布时应新建当前版本/配置/适用数据备份，并验证恢复点。
- 主站后端曾引用 20260930-live-baseline/backend，禁止清理该目录或其它历史版本，直至实际确认引用与回退路径。
- 新 /ui-lab/、/projects/、/tools/、/services/、/contact/、/privacy/ 预期由门户 SPA fallback 接管；逐路径确认不会覆盖九个独立静态应用的 alias。主站新增路由不需要迁移旧应用地址。
- 现金流、生活日历与各原生手账有不同公共模块/离线壳发布状态。只打包各自构建白名单，不能把根 shared/、源码、.ops、测试、DSH 会话、密钥或私有数据目录当静态资源发布。
- 原生应用修改 sw.js/CSS/HTML 后先构建并确认缓存版本；新构建取代旧壳的行为需验收，不能用强制刷新清除用户草稿。

## 发布步骤（待授权后执行）

1. 从已审查的干净提交构建；为每个实际变动应用建立独立版本目录，校验文件 SHA-256、来源提交和构建摘要。
2. 更新特定版本发布脚本的前版本检查与资源摘要；不原样重跑旧脚本。门户与各应用分别切换 current，保留可回退版本。
3. 如需修改路由，只改必要映射，检查 Nginx 语法后按实际管理方式重载。仅更新静态文件时不重启现有后端。
4. 公网逐文件校验与旧路径冒烟，检查主站、九子站、API health/tools/shows；MIO 仅验证既有可用性，不发布或修改。
5. 使用隔离上下文复跑导航、实际文件传输、离线壳、草稿和四种视口；全程用合成数据，不能把真实日记/财务/身体/照片上传测试服务。

## 回退

门户及独立应用分别原子切回各自上一版本；不清空浏览器存储，不重置数据库。标准导出只是新增格式，主存储仍是原格式；回退旧 UI 后仍应能读取原记录。新增恢复点为独立键，旧 UI 不会使用它；需要时先下载/保全，再根据明确数据删除要求处理。

如果发布过程涉及反代配置，按本次实际备份做最小逆向更改，不盲目覆盖整份历史配置。恢复数据库必须先核对当前写入并单独决策，不把静态版本回退当作数据库回退。
